# 渲染性能基线与后续优化计划

记录日期：2026-10-09。本文保留问题 3 的诊断与优化方案，供后续实施；本次特殊方块和材质正确性修复不代表这些性能任务已经完成。

## 诊断环境与方法

Windows 11、Python 3.12.7、Chrome 154.0.8037.98、ANGLE/Direct3D11、RTX 5060 Ti。独立无头 Chrome，1440×1000 视口，devicePixelRatio=1；实际工作区画布小于整个视口。资源是官方 Java 1.20.1，杜鹃教堂 36,094 格、62 分块，场景修订 3。

只读独立 runner 测量 Python 渲染数据组装、Three.js renderer.info、相机绘制提交与剖切重建。原始本地诊断文件是 `artifacts/profile_output/inspect_rendering.py` 与 `render-profile.json`，由 Git 忽略；运行前需要对应本地项目及服务，脚本不是通用性能测试套件。

浏览器 CPU 提交时间、`gl.finish()` 同步耗时、用户交互延迟分别记录。同步调用会改变流水线行为；不能直接将其视为实际稳定 FPS。嵌入浏览器、其他 GPU 和其他窗口尺寸需要另测。

HTTP 响应包含当时服务条件，不全是纯算法耗时；缩略图数字只代表生成步骤，不包含串行材料请求。pixelRatio 对比样本少、首次上传干扰明显，不据此推断 GPU 填充率瓶颈。60 FPS 的单帧预算约 16.7 ms，当前 CPU 提交已经超过它。

## 已定位原因

1. `frontend/src/viewer.ts` 按分块、状态模型和可见面 mask 建立 InstancedMesh。同状态能实例化，但教堂的状态/连接形状丰富，产生数千个小批次，增加 CPU 调用和驱动开销。
2. `setLayer()` 在每次滑条 input 时重建所有分块。连续拖动会占用主线程。
3. `adapters/rendering/packets.py` 即使 known_versions 全匹配，仍遍历所有格、序列化并哈希；每个格重复计算 model_id，cProfile 在一次调用中记录 72,188 次。
4. 前端 update 仍重建全场景 occupied 索引；refresh 另读取摘要。增量网络传输没有让全部 CPU 工作自动成为增量。
5. 缩略图复用主 renderer，改变主画布尺寸并 toDataURL，材料请求串行。频繁切换和搜索可能干扰交互。
6. 双面绘制、持久绘图缓冲、缓存及被替换网格的 GPU 对象生命周期也应测量，但当前数据尚未证明它们是首要瓶颈。

## 按优先级实施

| 顺序 | 任务 | 实现方向 | 验收重点 |
| --- | --- | --- | --- |
| 1 | 减少绘制批次 | 每分块按不透明/镂空/半透明材质合并静态几何；重复复杂构件按实际收益实例化 | 先证明 draw calls 显著下降，再核对 CPU/GPU 耗时；不得破坏透明顺序、选择与方块身份 |
| 2 | 增量后端 | 缓存规范状态 ID、分块摘要/版本；从提交差异确定受影响分块与邻居 | 无变化读取不扫描全部格；局部修改成本随变化范围增长 |
| 3 | 剖切与交互 | 滑条节流、仅重建穿过切层的分块；评估 shader clipping 快速预览 | 连续拖动稳定；剖切后内部面和射线选择正确 |
| 4 | 简单块面合并 | 对完整轴向块使用 greedy meshing；复杂模型保留原几何 | 材料、UV 重复、光照与透明边界不变；三角形下降且无可见接缝 |
| 5 | 主线程解耦 | Web Worker 生成网格，用可转移 typed arrays；版本校验和任务取消 | 旧任务不能覆盖新修订；主线程长任务减少 |
| 6 | 缩略图独立与缓存 | 独立小 renderer / 画布，按资源哈希+状态缓存；批量/有限并发获取模型 | 搜索、翻页不改变主画布；内存有界，资源版本切换正确 |
| 7 | 缓存与绘制细节 | 释放被替换实例网格；有界几何缓存；截图时才保留缓冲；合理使用单双面与像素比 | 长时间编辑/切层无持续内存增长；画面与截图正确 |

合并网格后需要保存 triangle/face 到方块的映射，或改用空间索引拾取。半透明内容的正确排序不能为了减少批次而丢弃。流体/告示牌等上下文模型要在邻居或关联数据变化时失效缓存。

## 后续测量与完成条件

固定同一机器、浏览器、资源、视口、相机与场景版本，先热身再多次采样；每次提交记录 draw calls、三角形、CPU 提交、GPU 同步样本、帧时间 P50/P95、长任务、内存、首次载入、局部 100/1,000 格编辑和导出。

场景覆盖木屋、36,094 格教堂与 100,000 格扩展样例；分别测相机、连续剖切、连续编辑、材料搜索及前后对比。性能和渲染正确性共同验收；保存/导出与独立读取器的正确性检查保持通过。

当前 P4/P5 门槛保留不动。后续可在实施前设定更高目标，例如教堂相机帧 P95 接近 16.7 ms；达不到时如实报告，不通过减少显示内容或改阈值掩盖结果。100,000 格尚未是已验证的流畅规模。

## 客户端形态与性能

| 形态 | 预期影响 | 成本与边界 |
| --- | --- | --- |
| Electron/Tauri 桌面壳 + 当前 Three.js | 通常不会自动减少 draw calls、网格重建和 JSON 工作；独立窗口可能避开嵌入浏览器竞争 | 易复用；Tauri 较小的壳体积不等于更快的 GPU 渲染 |
| 原生桌面渲染器 | 可以使用更直接的图形 API、任务线程与批处理 | 需要重写材质、模型、透明、拾取与 UI；未优化的原生实现也会卡 |
| Minecraft 客户端模组中的预览 | 可以复用游戏的方块、流体与方块实体渲染 | 版本、模组、运行环境、主线程同步和离线设计空间有新约束；仍需实测大建筑性能 |

建议先在现有工作台优化已经测到的瓶颈，再按安装体验决定是否增加桌面壳。若选择游戏客户端作为权威视觉验收，应通过接口连接 Python 场景，明确修订与坐标，而不是把格式、存储和编辑逻辑重写在多个入口里。
