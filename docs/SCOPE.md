# 范围与验收

## 产品目标

人和 AI 在同一份可版本化、可预览的 Minecraft 方块场景中设计建筑，支持批量几何创作与逐格细节。用户查看材料、修改建筑、选择版本并导出蓝图；AI 通过工具读取同样的资料、提交编辑、获得实际画面反馈。

设计目标由平台维护，不要求模型一次输出整栋建筑的所有坐标。

总目标与三个交付点见 [项目目标](GOALS.md)，逐阶段任务见 [实施路线](ROADMAP.md)。基础工作台、外部 AI 工具和平台内自主设计分别验收；完整项目包含后续自主设计流程，基础工作台可以先交付。

## 当前范围

首个游戏版本基线为 Java 1.20.1。新增版本必须有对应注册表、资源清单和兼容验收，不能只改变工作区的版本字符串。Bedrock 与模组方块暂不纳入首版。

“完整方块目录”是可核对的版本注册集合。每项保留稳定名称、合法状态、默认值和资源覆盖信息，中文名与分类作为搜索元数据。

“所有建筑”没有固定全集。已有建筑作为有来源的可选资产导入；参数化构件作为设计便利工具，不能限制 AI 只能从固定成品房型挑选。

首版提供完整注册目录，但仅在有准确支持的模型上显示实际外观。特殊/不可见/缺资源三者明确区分。不能给缺失模型换一个彩色立方体然后声称完整覆盖。特殊内容保存与特殊内容渲染是两项验收。

旧原型的解析经验已移植到新平台。当前实际模型和贴图来自独立导入的官方 1.20.1 客户端，全状态分类已核对；特殊渲染仍有明确限制。具体兼容范围见 [资源与限制](RESOURCES_AND_LIMITS.md)。

不进入当前实现：Blender、文生 3D、图生 3D、bot 施工、游戏服务器、家庭陪玩、完整红石/流体/重力模拟、多人实时协作。

## 分阶段完成条件

交付点 A 为人可用工作台，B 增加外部 AI 工具，C 增加平台自主设计并正式交付。共同要求持续复测。

| 条目 | 验收标准 | 对应阶段 |
| --- | --- | --- |
| 独立运行 | 从干净环境安装；移动目录后仍可启动；不依赖旧项目和 Codex 缓存 | P1 起，A/B/C 共同要求 |
| 材料目录 | 与指定版本注册表集合核对；分页不遗漏；非法名称/属性明确拒绝；每项展示准确的支持状态 | P2，A/B/C 共同要求 |
| 工作区 | 创建、保存、关闭重开、版本号和边界保持一致；结构化数据迁移有 schema 版本 | P3，A/B/C 共同要求 |
| 编辑 | 设置、填充、删除、替换、移动、复制、旋转、镜像及撤销/重做；批量操作错误不得部分提交 | P3/P5，A/B/C 共同要求 |
| GUI | 用户可以真实选择与修改场景；服务端修订一致；后续 AI 共用该场景 | P5，交付点 A |
| 预览 | 实际块模型和贴图、多角度、剖切、修改对比；缺资源及特殊渲染限制可见 | P4/P5，交付点 A |
| 蓝图 | `.litematic` 读取/写出；独立解析器逐格核对；受限内容保留或明确拒绝相关操作，导出损失不能静默发生 | P4，A/B/C 共同要求 |
| AI 工具 | 查询、局部观察、预演、提交、撤销/重做、实际多视图截图、导出；用户与 AI 共用应用服务 | P6，交付点 B |
| 自主设计 | 实际模型在预算内完成需求、创作、看图、修订与导出，记录人工反馈与失败案例 | P7/P8，交付点 C |
| 工程检查 | 格式、lint、类型、单元/契约/集成，以及对应阶段的前端检查和构建安装验收通过 | P1 起，按能力持续扩展 |
| 性能 | 小屋与 36,094 格教堂基准，记录载入、编辑、保存、导出；P6 起增加截图，明确机器和数据规模 | P4 建基线，P5—P8 复测 |

首版可以分里程碑交付，上表未满足的项必须保持未完成。基础工作台可先验收，不能在 AI 自动循环尚未实现时宣称“自主建筑设计师”完成。

## 性能目标与测量

建议后续使用 5,000、36,094 和 100,000 格三个规模；最后一个是扩展基准，不借用旧原型的上限作为性能承诺。先记录固定本机和低配机器基线，再确定发布门槛。

统计包括首次载入、相机交互、局部 100/1,000 格编辑、整组材质替换、保存重开、导出、峰值内存与前后画面。文件解码速度、WebGL 帧率和模型调用延迟分别测量。

## 数据正确性

区分材料名、完整 block state、实体/NBT 内容和游戏动态状态。多区域负尺寸、空气、长整数和未知标签不能在导入时丢失；已知不能无损导出的内容须给出逐项结果，并由调用者选择明确的受限输出。

场景修改后部分连接/形状可能在游戏邻接更新时改变。平台提供规则验证与可审查的规范化建议；超出规则覆盖的状态提示限制，不用“注册状态合法”证明游戏最终外观一致。
