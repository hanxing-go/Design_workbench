# 渲染优化图解：从零读懂这次改动

这套说明面向没有图形编程基础的读者。每篇只讲一个点，用小例子说明原来的做法、慢在哪里、改动后的流程，以及为提速付出的代价。你不需要先读源码。

**推荐打开网页版本：[进入图解阅读器](index.html)。** 每一篇也有 Markdown 版本。网页可以点击图片放大，图示已保存为图片，离线也能看。

在文件管理器中进入项目的 `docs/rendering-guide` 文件夹，双击 `index.html` 就能阅读，无需启动项目服务。用阅读目录跳到某一篇，或用每篇底部的“下一篇”顺序阅读。

## 从哪里开始

先读 [00：屏幕里的建筑是怎样画出来的](00-start-here.md)。认识“方块数据、网格、材质、绘制调用、帧”这几个词之后，再按下表顺序阅读。第一遍可以只看每篇的开头、图示和末尾自检；第二遍再看步骤、实测和局限。

读到一张流程图时，沿箭头看事情发生的顺序。标有“优化前”和“优化后”的两条路线用于比较；带有条件的问题框表示程序要先判断，再选择路线。图里的少量方块或时间数字如果注明“示意”，只是为了说明机制，不代表真实测试规模。

## 怎样读实测数字

本轮最终实现对应源码提交 `100afea`；完整实验、测试命令、静态包哈希和历史结果保存在 [优化实验记录](../RENDERING_OPTIMIZATION_LOG.md)。图解解释“为什么这样做”，实验记录负责保存可复核的证据。

| 你看到的词 | 用普通话理解 | 常见误解 |
| --- | --- | --- |
| FPS | 每秒显示多少张画面，60 FPS约为每帧16.7毫秒 | 一次测到60，所有机器就都能60 |
| 帧间隔 | 相邻两次画面更新之间过去了多久 | 等同于某一个函数的执行时间 |
| P95 | 约95%的样本不超过这个时间 | P95就是最长时间或平均时间 |
| 毫秒（ms） | 一秒的千分之一，1000毫秒就是一秒 | 0.3毫秒的后端函数代表整个操作只需0.3毫秒 |
| 首次载入 | 还没有现成结果，需要读数据、建网格、上传资源 | 应当和重复刷新缓存一样快 |
| 热缓存 | 以前算好的结果仍在内存中，可以复用 | 数据有变化时也能一直用旧结果 |
| 绘制调用 | 程序向显卡提交的一次绘制工作 | 一次调用必然等于一个方块 |
| 完成延迟 | 从点击到最终完整结果准备好的等待 | 只要没有长任务，操作就会立即完成 |

图解里的不同指标不要直接相加，也不要把单项测试当作整个产品的帧率。十万个方块从约5–6 FPS改善到稳定阶段约60 FPS，是多项改动共同作用的结果。

## 已经做到什么，还剩什么

在记录的 Windows / RTX 5060 Ti / Chrome 154 环境中，十万方块最终包完成了两种像素密度的多次重复测试：稳定旋转、近景、剖切与连续切层的帧间隔P95约16.8毫秒；绘制调用由29,596降至243。真实教堂、城堡裁片与用户链接别墅投影另有对应测量，具体长短和版本见实验记录。

首次打开十万方块仍需约3.3–3.4秒，记录了一次54毫秒主线程任务；综合连续交互仍有孤立约50毫秒帧。编辑和前后对比还需等待最终网格完成。严格像素对照尚未通过，部分边缘仍有差异。

完整115万方块城堡的约30 FPS属于历史候选包的压力探索，最终包没有重新测这份百万场景。用户链接别墅的原文件版本超出当前原生导入范围，本轮使用保留全部方块坐标与状态的渲染投影；原件的188个实体NBT没有进入投影渲染或新导出。这些边界不会因为流程图变简单而消失。

## 阅读约定

正文中的类比只是帮助理解。比如把缓存比作书柜，意味着“结果可以暂存”，并不意味着计算机真的逐个打开实体柜子。每篇都会说明对应关系和容易混淆的地方。

每篇结尾都有带答案的小问题。能用自己的话回答，就已经理解了这个优化点；源码链接留给想继续深入的人，不是读懂正文的前提。
